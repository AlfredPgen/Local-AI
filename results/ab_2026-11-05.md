# GPU A/B experiments, 2026-11-05 (RTX 3070 Laptop, 8 GiB)

Three experiments run while the 216M run (tinyGPT_muon) was paused at step 12,000, each arm at most 15 minutes, one
GPU job at a time, in a scratch output folder (results/experiments.csv of this repo was not written). The GPU kept
switching between about 85 W (boost, ~1.2-1.4 GHz) and its 55 W cap (throttled, ~0.3-0.8 GHz) during the day, so raw
speeds are only compared within one regime. Decision rule for quality: act only on differences above 0.02 bits per
byte (the seed-to-seed noise at this scale is about 0.005-0.01; the GPU non-determinism floor seen here is 0.0003).

What changed in tiny_gpt.py because of them (commit "A/B consequences"):

| experiment | result | consequence in the code |
|---|---|---|
| S1 | micro 2 x 132 without checkpointing is 5-16 % faster than 4 x 66 with it, same loss | none (the planner rule from WP2-A stays) |
| Q: QK-norm | -0.106 bpb | stays on for new runs |
| Q: learning rate | x2 beats x1 by 0.060 (d 384); x4 beats x2 at both sizes | LR_TABLE x2, default weight decay 0.1 -> 0.05 (lr x wd unchanged) |
| Q: EMA | never better; 1.1 bpb worse at steps 300/400 (initial-weight bias) | default off (`--ema on` / `--ema 0.999` opt-in); the average is now debiased |
| Q: document mask | -0.0016 bpb at ctx 512 (noise) for ~8 % more forward+backward time | stays opt-in; no planner default at ctx >= 2048 (unmeasured) |
| M1: MoE | memory within the estimate; 2.2-2.3x slower than dense; behind dense on loss at step 50 | none: dense stays the default, the MoE memory terms already fit |

The running run is unaffected: --resume keeps the learning rate, weight decay, EMA setting, QK-norm and document mask
recorded in its checkpoint.

Q5 cost, interleaved bench (same d 384 model compiled, BF16, micro 16 x 512, forward + backward of the full loss, two
compiled copies timed alternately, 12 rounds of 8 micro-steps): plain 0.081-0.093 s, doc mask 0.089-0.097 s per
micro-step; paired ratio median 1.078 (range 1.042-1.106), i.e. ~8 % of forward+backward, ~5-6 % of a whole step.
Peak memory +0.01 GiB.

Raw tok/s is not comparable between arms (clock swings of up to 1.5x); s/step = 65,536 / tok/s.

Decisions:

1. QK-norm: Q1 vs Q0 -0.106 bpb (pmc -0.096, arxiv -0.142), the gap open from step 200 on. Stays on for new runs.
2. Learning rate: d 384 x2 vs x1 -0.060, x4 vs x2 -0.019 (borderline, same direction); d 512 x4 vs x2 -0.047 (x1
   not run: the 110-minute GPU cap was reached). Both sizes put the 500-step optimum at or above x4. A 500-step
   optimum over-states the rate of a 60,000-step run by about 1.7x (DeepSeek LLM's C^-0.125 compute term):
   4 / 1.7 = 2.35, so the measured arm below it, x2, is applied: LR_TABLE x2 with the slope kept, and the default
   weight decay 0.1 -> 0.05 so lr x weight decay (the shrink per step, 1 / timescale) is unchanged. AdamW alone was
   not swept. Check at real size: stop the first long run with the new table at 2,000 steps if its bpb is worse than
   an old-table run at the same step.
3. EMA: no gain in 500 steps. The average started as a copy of the initial weights with no bias correction, so at
   step 300 it still held 0.990^30 = 74 % of them (67 % at step 400). Default now off (`--ema on` or `--ema 0.999`
   for long runs), and the average is debiased (Adam-style: the n-th update uses decay d (1 - d^(n-1)) / (1 - d^n),
   so the first update replaces the starting copy). Its stable-phase gain is still untested.
4. Document mask: -0.0016 bpb at ctx 512 (noise) for ~8 % more forward+backward time. Stays opt-in; ctx >= 2048 is
   unmeasured, so the planner does not switch it on there.

of hidden 1024, 2 per token, softmax router, bias balancing (lb-loss 0, router z-loss 1e-3, bias rate 1e-3), loop
implementation, every block MoE: 297.6M total / 99.4M active parameters (dense: 99.3M). Peak lr 6.01e-4, warmup 50.

Pass criteria (2 of 5):

- memory within the estimate: pass (5.02 GiB allocated against the planner's 5.3; ratio 0.95)
- s/step within 1.5x of dense: fail (same 55 W regime: 2.33x the planner's dense arm, 2.19x dense with the same
  checkpointing and micro-batch)
- moe_load_max < 1.5 at step 50: fail (3.34; per layer 1.25-3.34). By design not reachable: with bias rate 1e-3 the
  balancing bias moves at most 0.05 in 50 steps
- dead experts 0: pass
- loss curves overlapping: fail (0.22 nats behind in train loss at step 45; val +0.26 nats at step 50)

Consequences: dense stays the default; no `--experts auto`; no MoE run on the laptop. The MoE memory terms of
estimate_train_bytes need no change (estimate 5% above the allocated peak). The dense estimates were 5-7 % below the
allocated peak (4.372 vs 4.1, 2.744 vs 2.6 GiB) and S1b's 2 % above it, all inside the 0.7-1.3 band in which WP2-B
leaves the calibration alone. Open items: profile the loop implementation under compile (the `counts.tolist()`
host sync in every MoE block of every micro-batch and graph breaks between experts are the likely cost) and try
`--moe-impl grouped`; judge balance at 500+ steps or with `--balance both --lb-loss 0.01`; measure peak_mem_gib for
the micro 16 x 4 checkpointed dense plan, whose 5.4 GiB estimate paged on the device (no metrics row was written, so
the estimate could not be checked against the allocator).
